Documentation - Workflow Planning

Guide complet de la saisie et gestion des plannings d'activités

Vue d'ensemble du module Planning

Le module Planning est au cœur de la gestion opérationnelle de l'application Hydria. Il permet aux employés de saisir leurs activités quotidiennes en fonction de leur poste, de gérer les détails de chaque intervention (équipements, points d'eau, déplacements), et d'assurer un suivi précis des coûts et des ressources utilisées.

Ce module intègre plusieurs concepts clés :

  • Restriction par poste : Chaque employé ne peut saisir que les activités autorisées pour son poste via la table Poste_Activites
  • Filtrage contextuel : Les équipements et points d'eau sont automatiquement filtrés en fonction de l'ouvrage sélectionné dans le planning
  • Calcul automatique : Les prix unitaires sont pré-remplis depuis la table Designation et les coûts de déplacement sont calculés automatiquement
  • Traçabilité complète : Chaque détail de planning est lié à un employé, une date, une activité et peut inclure des informations comptables (numéro DiameX)
  • Intégration comptable : Les détails peuvent être exportés vers le système DiameX via la table TemporaireDiameX

Étape 1 : Sélection de la date et identification du poste

Lorsqu'un employé accède à la page de plannings (/plannings/), le système identifie automatiquement son poste via la relation Employe → Poste. Cette information est cruciale car elle détermine quelles activités seront disponibles pour la saisie.

  • L'employé sélectionne la date pour laquelle il souhaite saisir un planning
  • Le système récupère le poste actuel de l'employé (table Employe.poste_id)
  • Si l'employé n'a pas de poste assigné, il ne peut pas créer de planning

Étape 2 : Récupération des activités autorisées

Le système interroge la table Poste_Activites pour déterminer quelles activités sont autorisées pour le poste de l'employé. Cette table de liaison définit les permissions granulaires au niveau de chaque poste.

  • Requête SQL : SELECT activite_id FROM poste_activites WHERE poste_id = ?
  • Seules les activités liées au poste sont affichées dans le dropdown de sélection
  • Exemples : Un "Technicien" peut avoir "Réparation fuite", "MP pompe", etc.
  • Un "Administrateur" peut avoir "Bilan mensuel", "Relevé compteur", etc.

Étape 3 : Saisie conditionnelle selon le type d'activité

En fonction de l'activité sélectionnée, le formulaire affiche différents champs. Cette logique conditionnelle est implémentée en JavaScript côté client pour une meilleure réactivité.

Type d'activité Champs requis Champs optionnels Exemple
Réparation Désignation, Quantité, Ouvrage Équipement, Point d'eau, Trajet Réparation fuite sur BP #123
Livraison Désignation, Quantité, Magasin, Acheteur Trajet, Compte Livraison tuyaux PVC à Ambanja
MP/Bilan/Relevé Ouvrage Observations Maintenance préventive pompe AEP

Étape 4 : Gestion des désignations et prix unitaires

Pour les activités nécessitant une désignation (Réparation, Livraison, Avance, Recette), le système propose une liste déroulante filtrée par type de désignation. Chaque désignation possède un prix unitaire qui est automatiquement rempli lors de la sélection.

  • Types de désignations :
    • Avance : Avance sur salaire ou prestation
    • Bon de livraison : Fournitures et matériaux
    • Recette : Encaissement ou paiement forfaitaire
  • Auto-remplissage du prix unitaire :
    • Champ Designation.prix_unitaire récupéré automatiquement
    • L'employé peut modifier le prix si nécessaire (cas exceptionnel)
    • Le montant total est calculé : Montant = Quantité × Prix Unitaire
  • Champs conditionnels par type :
    • Bon de livraison : Magasin + Acheteur requis
    • Recette : Compte comptable requis
    • Avance : Prix auto-rempli, pas de champ supplémentaire
Mise à jour automatique des prix (workflow Caissière) :
Lorsqu'un ticket de type "Avance" est validé en retour par la caissière, le système met automatiquement à jour le champ prix_unitaire de la désignation si celui-ci est NULL ou si la date du planning est plus récente que la date_prix existante.

Étape 5 : Sélection d'équipement ou point d'eau (filtrage par ouvrage)

Si la désignation sélectionnée concerne un équipement constitutif ou un point d'eau (champs Designation.concerne_equipement ou concerne_point_eau), le système affiche une liste déroulante filtrée par l'ouvrage déjà sélectionné dans le planning.

  • Filtrage équipements :
    • Requête : EquipementConstitutif.objects.filter(ouvrage_id=ouvrage_selectionne)
    • Exemple : Si l'ouvrage est "AEP Ambanja", seuls les équipements de cet ouvrage apparaissent
    • Types d'équipements : Pompe, Réservoir, Surpresseur, Chlorinateur, etc.
  • Filtrage points d'eau :
    • Requête : PointEau.objects.filter(ouvrage_id=ouvrage_selectionne)
    • Exemple : Si l'ouvrage est "AEP Ambanja", seuls les BP/BI/BF/Kiosques de cet ouvrage apparaissent
    • Affichage : Code point d'eau + Type + Parcelle (ex: "BP-001 - BP - Parcelle A123")
  • Bénéfices du filtrage :
    • Évite les erreurs de saisie (sélection d'équipement d'un autre ouvrage)
    • Améliore la rapidité de saisie (liste réduite et pertinente)
    • Garantit la cohérence des données

Étape 6 : Gestion des trajets et calcul des coûts de déplacement

Pour certaines activités nécessitant un déplacement (livraison, réparation terrain), l'employé peut saisir un trajet en sélectionnant un village de départ (Point A) et un village d'arrivée (Point B). Le système calcule automatiquement le coût du déplacement en consultant la table Deplacement.

  • Sélection du trajet :
    • Village A : Village de départ (souvent le siège de l'organisation)
    • Village B : Village de destination (lieu de l'intervention)
    • Moyen de transport : Taxi-brousse, Pirogue, Bac
  • Recherche du prix dans la table Deplacement :
    • Requête : Deplacement.objects.filter(village_a=A, village_b=B, moyen_transport=X).latest('date_prix')
    • Si le trajet existe : Récupération du prix_unitaire
    • Si le trajet n'existe pas : L'employé peut saisir le prix manuellement
    • Le prix le plus récent (date_prix) est toujours utilisé
  • Calcul du coût total :
    • Coût déplacement = prix_unitaire_deplacement × nombre_de_trajets
    • Montant total du détail = (Quantité × PU désignation) + Coût déplacement
Gestion des trajets manquants :
Si le système ne trouve pas de tarif pour un trajet donné (par exemple, un nouveau village ou un nouveau moyen de transport), l'administrateur doit créer une entrée dans la table Deplacement via la page Administration > Déplacements.

Étape 7 : Validation et création du PlanningDetail

Une fois tous les champs remplis, le système valide les données et crée un enregistrement dans la table PlanningDetail. Cet enregistrement lie le planning principal à tous les détails de l'intervention (désignation, équipement, point d'eau, trajet, montants).

  • Validations côté serveur :
    • Vérification que la désignation existe et est active
    • Vérification que l'équipement/point d'eau appartient bien à l'ouvrage sélectionné
    • Vérification que le montant calculé est cohérent (> 0)
    • Vérification que l'employé a bien le droit de créer cette activité
  • Champs enregistrés dans PlanningDetail :
    • planning_id : Référence au Planning parent
    • designation_id : Référence à la Désignation
    • quantite : Quantité saisie
    • pu : Prix unitaire (peut être modifié par l'employé)
    • montant : Montant calculé (quantité × pu + coût déplacement)
    • equipement_constitutif_id : Si applicable
    • point_eau_id : Si applicable
    • village_a_id, village_b_id : Si trajet
    • magasin, acheteur : Pour bons de livraison
    • compte : Pour recettes
  • Champs de tracking :
    • utilise : Boolean (True si ticket utilisé terrain)
    • retourne : Boolean (True si ticket retourné à caissière)
    • numeroDiameX : Rempli lors de l'export comptable
    • baseDiameX : Base DiameX concernée

Cas d'usage et exemples concrets

Exemple 1 : Réparation de fuite sur un branchement privé

Un technicien doit réparer une fuite sur un branchement privé (BP) à Ambanja. Voici le processus complet de saisie :

  • Date : 15 novembre 2025
  • Employé : Jean DUPONT (Poste: Technicien)
  • Activité autorisée : "Réparation fuite" (via Poste_Activites)
  • Ouvrage : AEP Ambanja
  • Désignation : "Réparation fuite tuyau" (Type: Avance)
  • Prix unitaire : 50,000 Ar (auto-rempli)
  • Quantité : 1
  • Point d'eau : BP-123 (filtré par ouvrage AEP Ambanja)
  • Trajet : Ambanja Centre → Village Antsahabe (Taxi-brousse)
  • Coût déplacement : 10,000 Ar (récupéré depuis table Deplacement)
  • Montant total : (1 × 50,000) + 10,000 = 60,000 Ar

Exemple 2 : Livraison de matériel

Un chauffeur livre des tuyaux PVC pour un chantier de réhabilitation. La saisie inclut des informations sur le magasin et l'acheteur :

  • Date : 16 novembre 2025
  • Employé : Paul RAKOTO (Poste: Chauffeur)
  • Activité autorisée : "Livraison matériel"
  • Ouvrage : AEP Nosy Be
  • Désignation : "Tuyau PVC Ø 63mm" (Type: Bon de livraison)
  • Prix unitaire : 15,000 Ar/mètre
  • Quantité : 50 mètres
  • Magasin : "Quincaillerie Ambanja"
  • Acheteur : "SOAKOJA"
  • Trajet : Ambanja → Nosy Be (Bac + Taxi-brousse)
  • Coût déplacement : 35,000 Ar
  • Montant total : (50 × 15,000) + 35,000 = 785,000 Ar

Exemple 3 : Maintenance préventive (sans désignation)

Un technicien effectue une maintenance préventive mensuelle sur une pompe. Cette activité ne nécessite pas de désignation ni de détails :

  • Date : 1er novembre 2025
  • Employé : Luc ANDRIAMANITRA (Poste: Technicien)
  • Activité autorisée : "MP pompe"
  • Ouvrage : AEP Ambanja
  • Détails : Aucun (pas de PlanningDetail créé)
  • Observations : "Vérification routine mensuelle - RAS"

Règles métier et contraintes CRITICAL

Contraintes d'intégrité référentielle :
• Un PlanningDetail ne peut PAS être créé sans un Planning parent
• Un PlanningDetail ne peut PAS référencer un équipement d'un autre ouvrage
• Un PlanningDetail ne peut PAS référencer un point d'eau d'un autre ouvrage
• Un employé ne peut PAS saisir une activité non autorisée pour son poste
Règles Timezone (CRITICAL) :
• Les dates de planning sont stockées en UTC mais affichées en timezone Madagascar (Indian/Antananarivo)
• Import : Utiliser tz_madagascar.localize(date_naive) (PAS make_aware)
• Affichage : Convertir avec .astimezone(tz_madagascar) avant .date()
• Filtres : Filtrer en Python APRÈS conversion timezone (JAMAIS en SQL avec AT TIME ZONE)
Règles de calcul :
• Le montant est TOUJOURS recalculé lors de la modification : Montant = Quantité × PU + Coût déplacement
• Les prix unitaires peuvent être modifiés manuellement (cas exceptionnel)
• Le coût de déplacement est toujours ajouté au montant de la désignation (pas un champ séparé)
• Les montants sont stockés en Decimal pour éviter les erreurs d'arrondi
Workflow d'utilisation terrain (Caissière) :
1. L'employé reçoit un ticket imprimé (QR Code) avec le PlanningDetail
2. Sur le terrain, il marque le ticket comme utilisé (utilise=True)
3. Il retourne le ticket physique à la caissière
4. La caissière scanne le QR Code et valide le retour (retourne=True)
5. Pour les bons de livraison : Le stock est automatiquement décrémenté
6. Pour les avances : Le prix unitaire de la désignation est mis à jour si nécessaire
7. Une ligne est créée dans TemporaireDiameX pour export comptable

Intégration avec les autres modules

Le module Planning est étroitement lié à plusieurs autres modules de l'application. Voici les principales interactions :

1. Module Employees (Employés et Postes)

  • Relation : Planning.employe_id → Employe.id
  • Usage : Identification de l'employé qui saisit le planning
  • Filtrage : Activités autorisées via Employe.poste → Poste_Activites
  • Permissions : Chaque employé ne voit que ses propres plannings (sauf administrateurs)

2. Module Organization (Ouvrages)

  • Relation : Planning.ouvrage_id → Ouvrage.id
  • Usage : Définir sur quel ouvrage porte l'intervention
  • Filtrage : Équipements et points d'eau filtrés par ouvrage
  • Statistiques : Nombre d'interventions par ouvrage, coûts par ouvrage

3. Module Infrastructure (Équipements)

  • Relation : PlanningDetail.equipement_constitutif_id → EquipementConstitutif.id
  • Usage : Lier une intervention à un équipement spécifique (pompe, réservoir, etc.)
  • Traçabilité : Historique des interventions par équipement
  • Maintenance : Planification des MP (Maintenance Préventive)

4. Module Billing (Points d'eau)

  • Relation : PlanningDetail.point_eau_id → PointEau.id
  • Usage : Lier une intervention à un point d'eau spécifique (BP, BI, BF, Kiosque)
  • Géographie : Via PointEau.parcelle, on accède au village et à la commune
  • Client : Possibilité de notifier l'usager d'une intervention

5. Module Geography (Villages et Déplacements)

  • Relation : PlanningDetail.village_a_id → Village.id
  • Usage : Définir le trajet pour calcul des frais de déplacement
  • Calcul : Recherche du prix dans Deplacement selon villages et moyen de transport
  • Statistiques : Analyse des déplacements par zone géographique

6. Module Inventory (Stocks)

  • Relation : Via Designation → Product (pour bons de livraison)
  • Usage : Lorsqu'un bon de livraison est validé, le stock est décrémenté
  • Workflow : Caissière valide retour → Stock.quantite -= PlanningDetail.quantite
  • Alerte : Si stock insuffisant, avertissement lors de la saisie

7. Module Accounting (Comptabilité DiameX)

  • Relation : PlanningDetail.numeroDiameX stocke le numéro de pièce comptable
  • Export : Lors de la validation retour, création d'une ligne dans TemporaireDiameX
  • Champs exportés :
    • description : Nom de la désignation
    • info : Informations complémentaires
    • pers : Nom de l'employé
    • detail : Détails (surnom employé)
    • montant_out : Montant du PlanningDetail
    • scan : Chemin vers le scan du ticket (si existe)
  • Synchronisation : Export manuel ou automatique vers DiameX via script

Questions fréquentes (FAQ)

Pourquoi je ne vois pas certaines activités dans la liste déroulante ?

Les activités affichées sont filtrées en fonction de votre poste. Seules les activités autorisées pour votre poste (définies dans la table Poste_Activites) sont disponibles. Si vous pensez qu'une activité devrait être disponible, contactez votre administrateur pour qu'il mette à jour les permissions de votre poste.

Comment modifier un planning déjà saisi ?

Vous pouvez modifier un planning en cliquant sur le bouton "Modifier" dans la liste des plannings. Cependant, si le planning a déjà été utilisé terrain (utilise=True) ou retourné à la caissière (retourne=True), la modification peut être restreinte. Dans ce cas, contactez votre administrateur.

Pourquoi le prix unitaire ne se remplit pas automatiquement ?

Le prix unitaire s'auto-remplit uniquement si la désignation sélectionnée possède un champ prix_unitaire renseigné. Si le champ est vide (NULL), vous devrez saisir le prix manuellement. Cette valeur sera ensuite mise à jour automatiquement lors de la validation du retour par la caissière (pour les avances uniquement).

Comment fonctionne le calcul automatique du coût de déplacement ?

Lorsque vous sélectionnez un Village A (départ) et un Village B (arrivée), ainsi qu'un moyen de transport (Taxi-brousse, Pirogue, Bac), le système recherche dans la table Deplacement le prix le plus récent correspondant à ce trajet. Si aucun prix n'est trouvé, vous devrez le saisir manuellement. Pour ajouter un nouveau trajet de manière permanente, allez dans Administration > Déplacements.

Que se passe-t-il si je sélectionne un équipement qui n'appartient pas à l'ouvrage ?

Cela ne devrait pas être possible ! Le système filtre automatiquement les équipements en fonction de l'ouvrage sélectionné dans le planning. Vous ne verrez que les équipements qui appartiennent à l'ouvrage choisi. Si vous rencontrez ce problème, il peut s'agir d'un bug : signalez-le immédiatement à l'administrateur.

Puis-je supprimer un PlanningDetail après sa création ?

Oui, tant que le ticket n'a pas été utilisé terrain ou retourné à la caissière. Si utilise=False et retourne=False, vous pouvez supprimer le détail via le bouton "Supprimer" dans la liste. Une fois utilisé ou retourné, seul un administrateur peut effectuer la suppression pour des raisons de traçabilité.

Comment savoir si mon planning a été exporté vers DiameX ?

Si le champ numeroDiameX est renseigné dans le PlanningDetail, cela signifie que le détail a été exporté vers le système comptable DiameX. Vous pouvez vérifier ce champ dans la colonne "N° DiameX" du tableau des plannings. Si la colonne est vide, l'export n'a pas encore été effectué.
