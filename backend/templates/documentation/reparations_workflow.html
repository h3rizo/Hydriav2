Workflow Réparations & Réhabilitations

  • Documentation
  • Réparations & Réhabilitations

Vue d'ensemble

Le module Réparations & Réhabilitations permet de gérer l'ensemble du cycle de vie des interventions techniques sur les ouvrages hydrauliques, depuis le signalement initial jusqu'à la validation finale des travaux. Ce système assure une traçabilité complète grâce à un workflow strict à 5 étapes et un historique automatique de toutes les actions.

Contrairement à un système de ticketing classique, ce workflow impose des transitions de statut séquentielles (on ne peut pas passer directement de "Signalée" à "Terminée"), garantissant ainsi que chaque étape clé du processus est documentée : planification, exécution, compte-rendu et validation.

Le système offre deux modes de visualisation complémentaires : une vue liste avec filtres avancés pour la recherche et le reporting, et une vue Kanban pour une vision d'ensemble rapide de l'avancement des travaux par statut.

Étapes Détaillées du Workflow

1 Signalement de la réparation

Description

La première étape consiste à créer un signalement de réparation lorsqu'un problème est détecté sur un ouvrage (panne, fuite, dysfonctionnement, dégradation, etc.). Le signalement peut être effectué par un employé lors d'une tournée terrain, ou suite à une réclamation d'usager.

Champs obligatoires

  • Ouvrage concerné : Sélection dans la liste des ouvrages existants
  • Description du problème : Texte libre détaillé (minimum recommandé : 20 caractères)
  • Priorité : Critique / Haute / Moyenne / Basse
  • Signalé par : Employé enregistrant le signalement (auto-rempli si connecté)

Champs optionnels

  • Nom de l'usager : Si signalement provient d'un usager
  • Contact usager : Téléphone ou email pour suivi
  • Équipement constitutif : Si le problème concerne un équipement précis (pompe, vanne, etc.)
  • Point d'eau : Si le problème concerne un point d'eau spécifique
  • Coût estimé : Estimation préliminaire du coût de réparation (en Ar)
  • Observations : Informations complémentaires

Automatisations

  • Génération automatique d'un numero_reference unique (ex: REP-2025-00123)
  • Statut initial fixé à Signalée
  • Date de signalement enregistrée automatiquement
  • Création de l'entrée initiale dans l'historique
  • L'usager n'est PAS automatiquement informé (usager_informe=False)
Astuce : Pour les signalements critiques (coupure d'eau, risque sanitaire), utiliser la priorité "Critique" pour qu'ils apparaissent en tête de liste.
2 Planification de l'intervention

Description

Une fois le signalement validé par un responsable, l'intervention doit être planifiée. Cette étape consiste à définir une date prévue pour les travaux et à assigner un agent technique ou une équipe responsable de l'exécution.

Actions requises

  • Saisir la date prévue : Date à laquelle les travaux devraient démarrer
  • Assigner un agent : Employé responsable de la réparation

Automatisations

  • Statut passe à Planifiée
  • Entrée ajoutée dans l'historique avec l'auteur de l'action
  • L'agent assigné peut consulter ses réparations planifiées via filtre
Important : Une réparation planifiée peut être reportée en modifiant la date prévue et/ou en changeant l'agent assigné. Ces modifications sont tracées dans l'historique.
3 Démarrage des travaux

Description

Lorsque l'agent technique se rend sur le site et commence les travaux, il doit marquer la réparation comme "En cours". Cette action enregistre automatiquement la date et l'heure de début réel des travaux.

Actions requises

  • Cliquer sur le bouton "Démarrer" dans le dropdown d'actions
  • Confirmer le démarrage (popup de confirmation)

Automatisations

  • Statut passe à En cours
  • date_debut enregistrée automatiquement (date et heure actuelles)
  • Entrée ajoutée dans l'historique
  • La réparation apparaît dans la colonne "En cours" de la vue Kanban
Note : Si les travaux démarrent en retard par rapport à la date prévue, l'écart est visible dans l'historique (date prévue vs date début réelle).
4 Fin des travaux

Description

Une fois les travaux achevés sur le terrain, l'agent doit clôturer l'intervention en saisissant un compte-rendu détaillé et le coût réel des travaux. Cette étape permet de documenter ce qui a été fait concrètement et de comparer le coût réel au coût estimé initial.

Actions requises

  • Saisir le compte-rendu : Description détaillée des travaux effectués
  • Saisir le coût réel : Montant total dépensé (pièces + main d'œuvre) en Ariary

Automatisations

  • Statut passe à Terminée
  • date_fin enregistrée automatiquement
  • Calcul automatique de la durée réelle des travaux (date_fin - date_debut)
  • Entrée ajoutée dans l'historique avec compte-rendu et coût
Important : Si les travaux ne sont pas complets ou satisfaisants, le responsable peut faire repasser la réparation en statut "En cours" lors de la validation.
5 Validation de la réparation

Description

La dernière étape du workflow consiste à faire valider les travaux par un responsable technique ou un superviseur. Cette validation atteste que les travaux ont été correctement réalisés, que l'ouvrage est de nouveau opérationnel, et que le compte-rendu est conforme à la réalité.

Actions requises

  • Vérifier le compte-rendu et le coût réel
  • Cliquer sur le bouton "Valider"
  • Saisir un commentaire de validation (optionnel mais recommandé)

Automatisations

  • Statut passe à Validée
  • validee_par enregistre l'employé qui a validé
  • date_validation enregistrée automatiquement
  • Entrée finale ajoutée dans l'historique
  • L'historique complet est figé (modifications limitées)

Option "Informer l'usager"

Si la réparation concerne un usager identifié (nom et contact renseignés), un bouton "Informer usager" est disponible à tout moment du workflow. Cliquer sur ce bouton marque l'usager comme informé (usager_informe=True) et ajoute une entrée dans l'historique. Une icône apparaît alors dans le tableau pour indiquer que l'usager a été notifié de l'avancement.

Résultat : La réparation est clôturée et archivée. Les statistiques globales sont mises à jour, et le cycle de vie de cette intervention est terminé.

Règles Métier CRITICAL

Workflow strict : pas de saut d'étapes

Les transitions de statut doivent suivre l'ordre séquentiel. On ne peut PAS passer directement de "Signalée" à "Terminée". Les seules transitions autorisées sont :
• Signalée → Planifiée ou Annulée
• Planifiée → En cours ou Annulée
• En cours → Terminée ou Annulée
• Terminée → Validée ou En cours (reprendre si insatisfaisant)

Permissions et responsabilités

Qui peut créer : Tous les employés authentifiés
Qui peut planifier : Responsables et coordinateurs
Qui peut démarrer/terminer : Agent assigné uniquement
Qui peut valider : Responsables techniques et directeurs
Qui peut annuler : Responsables et directeurs (toute étape)

Historique automatique et traçabilité

Chaque action (création, changement de statut, information usager) génère automatiquement une entrée dans la table HistoriqueReparation avec :
• Date et heure précises de l'action
• Employé ayant effectué l'action (effectue_par)
• Nouveau statut (si changement)
• Description de l'action (automatique ou saisie manuellement)
L'historique est IMMUTABLE : une fois créée, une entrée ne peut pas être modifiée ou supprimée.

Filtres et recherche avancée

La vue liste offre 5 critères de filtrage combinables :
• Statut : Afficher uniquement signalées, planifiées, en cours, terminées ou validées
• Ouvrage : Filtrer par ouvrage spécifique (forage, AEV, etc.)
• Priorité : Critique, Haute, Moyenne ou Basse
• Assigné à : Réparations d'un agent technique spécifique
• Recherche textuelle : Chercher dans numéro référence, description ou nom usager
Astuce : Cliquer sur une carte statistique (ex: "3 En cours") filtre automatiquement le tableau selon ce statut.

Intégration avec Autres Modules

Le module Réparations ne fonctionne pas de manière isolée. Il s'intègre avec plusieurs autres modules du système Hydria pour offrir une vision complète du cycle de gestion des infrastructures :

Module Ouvrages

  • Lien : Chaque réparation est rattachée à un ouvrage spécifique
  • Impact : Historique des interventions visible dans la fiche ouvrage
  • Statistique : Nombre de réparations par ouvrage (indicateur de fiabilité)

Module Employés

  • Signalé par : Employé ayant créé le signalement
  • Assigné à : Agent technique responsable de l'exécution
  • Validé par : Responsable ayant approuvé les travaux
  • Planning : Les réparations assignées apparaissent dans le planning employé

Module Planning

  • Activité : Les réparations peuvent générer des activités "Réparation"
  • PlanningDetail : Pièces et matériaux utilisés sont tracés
  • Coût : Les dépenses sont comptabilisées dans les plannings mensuels

Module Équipements

  • Lien optionnel : Réparation peut concerner un équipement spécifique
  • Historique : Nombre d'interventions sur chaque équipement
  • Maintenance : Identifie les équipements nécessitant remplacement

Module Points d'Eau

  • Lien optionnel : Réparation peut concerner un point d'eau précis
  • Qualité service : Taux de disponibilité du point d'eau
  • Usagers : Impact sur la distribution d'eau

Module Comptabilité

  • Budget : Suivi des dépenses réelles vs estimées
  • Analytique : Coût total des réparations par période/ouvrage
  • Prévisions : Estimation budgets futurs basés sur historique

Module Reporting

  • Statistiques : Nombre réparations par mois, type, priorité
  • Délais : Temps moyen de résolution par type de panne
  • Performance : Taux de respect des délais prévus
  • Coûts : Analyse des écarts budget estimé vs réel

Questions Fréquentes (FAQ)

Peut-on modifier une réparation après sa validation ?

Non, une fois qu'une réparation est validée (statut Validée), elle est considérée comme clôturée et figée. Seul un administrateur système peut modifier les champs via l'interface d'administration Django. L'historique, quant à lui, est totalement immutable : aucune entrée ne peut être modifiée ou supprimée, même par un administrateur.

Si une erreur est détectée après validation, la bonne pratique est de créer une nouvelle réparation avec le bon numéro de référence et de documenter le lien dans les observations.

Comment annuler une réparation en cours ?

Cliquez sur le bouton "Annuler" dans le dropdown d'actions (disponible à toutes les étapes sauf "Validée"). Une popup vous demandera de confirmer l'annulation et de saisir une raison (optionnel mais recommandé).

La réparation passera au statut Annulée et sera archivée. Elle restera visible dans les listes avec filtre "Toutes" ou "Annulées", mais ne sera plus comptabilisée dans les statistiques actives.

Note : Une réparation annulée peut être "réactivée" par un administrateur en changeant manuellement son statut dans la base de données, mais cette opération doit rester exceptionnelle.

Quelle est la différence entre "Réparation" et "Réhabilitation" ?

Le module gère les deux types d'interventions, mais la distinction est principalement sémantique :

  • Réparation : Intervention ponctuelle pour corriger une panne ou un dysfonctionnement (ex: fuite, panne moteur, vanne bloquée). Durée courte (quelques heures à quelques jours).
  • Réhabilitation : Intervention plus lourde visant à remettre en état un ouvrage dégradé ou à améliorer ses performances (ex: remplacement complet d'une pompe, réfection du génie civil, extension du réseau). Durée longue (plusieurs jours à plusieurs semaines).

Techniquement, les deux utilisent le même workflow. Pour distinguer visuellement, utilisez :
• Le champ Priorité (réhabilitations souvent "Haute" ou "Critique")
• Le champ Description (préciser "Réhabilitation complète de...")
• Le Coût estimé (réhabilitations > 500K Ar généralement)

Comment exporter la liste des réparations en Excel ?

Actuellement, le module n'inclut pas de fonction d'export Excel intégrée. Cependant, vous pouvez utiliser deux méthodes alternatives :

  1. Copier-coller depuis le tableau : Appliquez vos filtres, sélectionnez le contenu du tableau dans le navigateur (Ctrl+A), copiez (Ctrl+C) et collez dans Excel. Les colonnes seront respectées.
  2. Export via API : Développeurs peuvent appeler l'API /plannings/reparations/api/list/ avec les paramètres de filtrage, puis convertir le JSON en CSV/Excel avec un script Python ou un outil comme Postman.

Fonctionnalité future suggérée : Ajouter un bouton "Exporter en Excel" qui génère un fichier .xlsx avec les données filtrées, similaire au module "Plannings > Export Excel".

Que se passe-t-il si l'agent assigné change de poste ou quitte l'entreprise ?

La relation assigne_a est une ForeignKey nullable (null=True). Si l'employé est désactivé ou supprimé dans le système, deux scénarios sont possibles :

  • Désactivation (employé.actif=False) : L'employé reste visible dans les filtres et historiques, mais n'apparaît plus dans la liste des agents assignables pour les nouvelles réparations. Les réparations déjà assignées conservent son nom.
  • Suppression (DELETE) : Si configuré avec on_delete=SET_NULL, le champ assigne_a sera mis à NULL. L'historique conservera toutefois le nom de l'employé dans les entrées passées (stocké en tant que texte dans effectue_par).

Recommandation : Ne jamais supprimer les employés, uniquement les désactiver (actif=False) pour préserver l'intégrité historique.

Peut-on gérer les pièces détachées utilisées lors d'une réparation ?

Le modèle Reparation ne gère pas directement les pièces détachées. Cependant, il est intégré avec le module Planning via les relations suivantes :

  1. Lors de la planification d'une réparation, créer un Planning pour l'agent assigné avec l'activité "Réparation".
  2. Ajouter des PlanningDetail avec :
    • Type désignation : "Bon de livraison"
    • Quantité et prix unitaire des pièces utilisées
    • Magasin et acheteur si applicable
  3. Le champ cout_reel de la réparation devrait inclure la somme des PlanningDetails.

Astuce : Mentionner le numéro de référence de la réparation (ex: REP-2025-00123) dans les observations du PlanningDetail pour faciliter le rapprochement comptable.

Comment utiliser efficacement la vue Kanban ?

La vue Kanban est optimale pour une gestion visuelle quotidienne des réparations en cours. Voici quelques bonnes pratiques :

  • Réunion matinale : Afficher la vue Kanban sur un écran partagé pour visualiser rapidement l'avancement des travaux et identifier les blocages.
  • Colonnes de priorité : Les cartes sont triées par priorité dans chaque colonne (Critique en haut, Basse en bas).
  • Actions rapides : Chaque carte a un bouton d'action contextuel (Planifier, Démarrer, Terminer, Valider) pour mettre à jour le statut sans ouvrir le modal.
  • Détails complets : Cliquer sur "Voir détails" dans une carte pour afficher le modal avec l'historique complet sans quitter la vue Kanban.

Limite : Le drag-and-drop (glisser-déposer entre colonnes) n'est pas implémenté dans la version actuelle. Les transitions de statut doivent être faites via les boutons d'action.
